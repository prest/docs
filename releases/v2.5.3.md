# v2.5.3

Released: October 30, 2026

[GitHub tag](https://github.com/prest/prest/releases/tag/v2.5.3) · [Compare v2.5.2...v2.5.3](https://github.com/prest/prest/compare/v2.5.2...v2.5.3)

**v2.5.3** is a **security** release. It fixes three advisories published against v2.5.2 and earlier: writes with no filter ([GHSA-r867-ghgv-mrp9](https://github.com/prest/prest/security/advisories/GHSA-r867-ghgv-mrp9)), the write field list ([#1072](https://github.com/prest/prest/pull/1072), [GHSA-h25q-9rmj-646h](https://github.com/prest/prest/security/advisories/GHSA-h25q-9rmj-646h)), and columns a read references but does not select ([#1083](https://github.com/prest/prest/pull/1083), [GHSA-48r9-g6f9-x3gm](https://github.com/prest/prest/security/advisories/GHSA-48r9-g6f9-x3gm)). Dependency bumps ([#1074](https://github.com/prest/prest/pull/1074), [#1077](https://github.com/prest/prest/pull/1077), [#1078](https://github.com/prest/prest/pull/1078)) ship in the same tag.

- **Docker:** `prest/prest:v2.5.3` (linux/amd64 and linux/arm64)
- **Go install:** `go install github.com/prest/prest/v2/cmd/prestd@v2.5.3`

{% hint style="danger" %}
**Upgrade from v2.5.2 or earlier now.** Every release up to v2.5.2 is affected by [GHSA-r867-ghgv-mrp9](https://github.com/prest/prest/security/advisories/GHSA-r867-ghgv-mrp9) (high, CVSS 8.1), [GHSA-48r9-g6f9-x3gm](https://github.com/prest/prest/security/advisories/GHSA-48r9-g6f9-x3gm) (high, CVSS 7.5), and [GHSA-h25q-9rmj-646h](https://github.com/prest/prest/security/advisories/GHSA-h25q-9rmj-646h) (high, CVSS 7.1).

All three fixes refuse requests that used to succeed:

- **`DELETE`, `PUT`, and `PATCH` with no filter** are **400**, whatever `restrict` is set to. `[access] allow_unscoped_writes = true` restores the old behavior.
- **With `restrict = true`, write bodies** that set a column outside the table's `fields` are **400**.
- **With `restrict = true`, reads** that filter, order, group, or count by a column outside `fields` are **403**.

See [Upgrading from v2.5.2](#upgrading-from-v252).
{% endhint %}

## Security

### Writes with no filter are refused ([GHSA-r867-ghgv-mrp9](https://github.com/prest/prest/security/advisories/GHSA-r867-ghgv-mrp9))

**High, CVSS 8.1.** Reported by Hama1cco.

`DELETE`, `PUT`, and `PATCH` on `/{database}/{schema}/{table}` build their SQL `WHERE` from the query string. With no filter there was no `WHERE`, so one request with an empty query string deleted or rewrote every row in the table.

From v2.5.3 such a request is refused before any SQL runs:

```
DELETE /db/public/orders
```

```json
{"error":"refusing DELETE without a WHERE condition: add a filter query parameter"}
```

- The status is **400**, with `PUT` or `PATCH` in the message for those methods. It applies with `restrict` on or off.
- `_returning`, `_page`, and other `_` parameters are not filters.
- A new setting turns the check off:

  ```toml
  [access]
  allow_unscoped_writes = false  # default; env PREST_ACCESS_ALLOW_UNSCOPED_WRITES
  ```

See [Permissions — Unscoped writes](../get-started/permissions.md#unscoped-writes-v253).

### Write bodies follow `fields` ([GHSA-h25q-9rmj-646h](https://github.com/prest/prest/security/advisories/GHSA-h25q-9rmj-646h))

**High, CVSS 7.1.** Reported by 11lunaric11. Fixed in [#1072](https://github.com/prest/prest/pull/1072).

Under `restrict = true`, the `fields` of an `[[access.tables]]` or `[[access.users.tables]]` rule limited reads only. A caller allowed to write a table could set any of its columns, for example `role` or `is_admin` on a users table.

From v2.5.3:

- A `POST`, `PUT`, `PATCH`, or `POST /batch/...` body that sets a column outside the rule's `fields` is **400** `{"error":"column \"role\" is not writable on this table"}`. Nothing is written.
- `fields = ["*"]`, or no `fields` on the rule, still allows every column on writes.
- The response to a write (the inserted row, `/batch` rows, and [`_returning`](../api-reference/parameters.md#returning-rows-from-writes-_returning) rows) shows only the columns the caller may **read**. A rule that grants `write` without `read` gets `{}`.

See [Permissions — Column permissions](../get-started/permissions.md#column-permissions-fields).

### Every column a read references is checked ([GHSA-48r9-g6f9-x3gm](https://github.com/prest/prest/security/advisories/GHSA-48r9-g6f9-x3gm))

**High, CVSS 7.5.** Reported by neyugNat. Fixed in [#1083](https://github.com/prest/prest/pull/1083).

`fields` filtered the columns a read selected, but not the columns it used anywhere else. `_count` built its own select list from the raw `_select`, so `_count` with `_join` or `_groupby` returned columns of tables the caller could join but not read. Filters, `_or`, `_order`, `_groupby` / `HAVING`, `_korder`, and `_time_bucket` could name any column, so a caller could find out a hidden value by filtering or sorting on it.

From v2.5.3:

- `_count` with `_join` or `_groupby` no longer returns columns the caller cannot read.
- Every column named by a filter, `_or`, `_order`, `_count`, `_groupby` (including `HAVING` and function arguments), `_korder`, or TimescaleDB `_time_bucket` must be readable. Otherwise the request is **403** `{"error":"column \"salary\" is not readable on this table"}`.
- On a `_join`, `table.column` is checked against that table's rule.

With `restrict = false` nothing changes. See [Permissions — Reads](../get-started/permissions.md#reads-every-referenced-column-is-checked-v253).

## Upgrading from v2.5.2

1. **Retag** to `prest/prest:v2.5.3` or `go install github.com/prest/prest/v2/cmd/prestd@v2.5.3`.
2. **Find writes with no filter.** Search client code and logs for `DELETE`, `PUT`, or `PATCH` on a table route with an empty query string. Add a filter that matches the rows you mean, such as `?id=$eq.42`. If a job really must touch every row, use a filter that matches every row (`?id=$notnull`), or set `[access] allow_unscoped_writes = true`.
3. **With `restrict = true`, check each `fields` list against what clients write.** A client that sets a column outside `fields` now gets **400**. Add the column to `fields` or stop sending it. Clients that read back write responses only get readable columns now, so a `write`-only rule returns `{}`.
4. **With `restrict = true`, check reads that filter, sort, group, or count.** They now get **403** on a column outside `fields`. Add the column to `fields` if the caller should see it.
5. **Merge duplicate table rules.** pREST uses one `[[access.tables]]` entry per table (the last of equally specific entries), so a separate `read` entry and `write` entry for the same table do not combine. That was already true before v2.5.3, but now that `fields` also limits writes, put every permission for a table in one entry. See [Permissions — Table permissions](../get-started/permissions.md#table-permissions).
6. **If you skipped [v2.5.2](v2.5.2.md),** follow [v2.5.2 — Upgrading](v2.5.2.md#upgrading-from-v251) too: reserved tables, catalog auth, and the `prest_queries` audit.
